#### 애쉬앤베일 [🌐](https://play.google.com/store/apps/details?id=studio.gameberry.anv&pcampaignid=web_share)
`2024.06 ~ 2026.06` `신규 개발/라이브` `Unity 2022`

- **전투 시스템**
  - 전투 시스템 확장
    - 버프 스킬만 사용하던 동료 캐릭터에 독립 전투 기능 추가
    - 스플래시 대미지, 추가 투사체를 발사하는 특수 투사체(디아블로2 얼음 보주) 등의 특수 스킬 구현
  - 전투 규칙 확장
    - 일반/보스 몬스터 형태의 일반 스테이지에서 던전과 신규 사냥터를 추가하며 다양한 전투 규칙이 생김
    - 보스 러시, 몬스터 웨이브, 시간제 사냥터 등 전투 규칙을 확장하고 partial 클래스로 파일을 나누어 관리함
    - 규칙을 하나의 독립 객체로 분리하여 처리하는 방식으로의 개선을 고려했으나 라이브 서비스의 안정성을 우선하여 기존 시스템의 변경 범위를 최소화함. 
  - 상태 이상 시스템 개선
    - 문제: 기존에는 상태 이상의 수가 적어 캐릭터에서 단순 bool 플래그를 통해 처리했으나, 다수의 신규 스킬을 추가하며 상태 이상의 종류가 늘어남
    - 해결: 상태 이상 베이스 클래스를 두고 캐릭터에서 제네릭 기반 등록/제거/관리 구조로 변경
    - 결과: 상태 이상 추가 시 캐릭터 코드의 수정 범위 감소, 등록/중복 처리/제거 등의 관리가 한 곳에서 처리되어 유지보수성 향상

- **라이브 서비스**
   - 핫픽스 솔루션 InjectFix 연동
     - 라이브 중 이슈가 생겨 빌드 업데이트가 필요할 경우, 검수 과정으로 인해 문제 해결이 늦어지는 상황이 종종 있어 필요성을 느껴 연구하여 도입함
     - 결과: 도입 후 7개월 간 긴급 이슈로 인한 빌드 업데이트 0회 유지
     - 이후 연동 방법과 사용 방법 등을 문서화 해 스튜디오에 공유함
   - 콘텐츠 확장 용이성 개선 
     - 문제: 퀘스트 메뉴에서만 사용되던 퀘스트가 이벤트 퀘스트 등의 다른 콘텐츠로 확장되어, 데이터 저장 위치와 사용 UI에 따른 분기 처리가 늘어남
     - 해결: 인터페이스를 사용하여 데이터 접근 방식을 추상화하여 기존 코드의 수정 없이 추가할 수 있도록 함
     - 결과: 콘텐츠 확장에 필요한 작업 범위 감소

- **최적화**
  - 플레이 과정에서 발생하는 성능 저하 구간을 확인하고 Unity Profiler를 활용해 병목 분석
  - 스탯 빌드 시간 단축
    - 문제: 스탯이 변경될 때 모든 스탯을 업데이트하여 병목 발생
    - 해결: 빌드한 스탯을 저장하고 변경된 스탯만 업데이트
    - 결과: 스탯 빌드 시간 300 ms → 45ms
  - 로딩 시간 단축
    - 해결: 백엔드 서비스의 데이터 로드 함수를 최신화하고 프레임 당 데이터 처리량 확장
    - 결과: 초기 로딩 시간 14초 → 9초
  - Generic Infinite Scroll, Static Layout Group 등 최적화 UI 컴포넌트 개발

- **에디터 툴 개발**
  - 맵 배치 툴: 수작업 중심의 맵 배치 과정을 툴로 개선하여 예상 작업 기간 단축 3일 → 1일
  - 데이터 스크립트 자동 생성: 테이블 기반 스크립트 자동 생성 툴 개발 
  - 전투 디버깅 툴: 실시간 전투 정보 확인 기능을 제공하여 밸런싱 작업 지원

- **뒤끝 연동**
  - 서버(그룹) 구분, 채팅, 우편, 랭킹 등
  - 이벤트성 월드 보스 콘텐츠 개발
    - 배경: 이벤트 신규 콘텐츠 개발 논의하여 방법 연구
    - 해결: 뒤끝에서 제공하는 유저 데이터의 값을 Add하는 함수 사용하여 서버 별 시스템 계정을 생성해 점수를 Add하도록 개발
    - 검증: 동시에 다수의 기기에서 반복적으로 점수를 전송하는 내부 테스트를 통해 안정성 검증

  - 인벤토리, 다이얼로그, 코스튬, 이벤트 패스 등 콘텐츠 개발

  - Silhouette, Planar Reflection, Skill Indicator

- **탄막 슈팅 시스템 개발**
  - 성능 최적화
    - 문제: Unity Physics를 사용했을 때 테스트 기기에서 300개 수준에서 60프레임 유지 실패하여 성능 개선 필요성
    - 해결: Physics를 사용하지 않고 수학 기반 충돌 판정을 사용하며, 충돌 연산 최적화
      - 원, OBB 형태의 충돌 판정
      - 공간 분할 알고리즘 사용: 쿼드 트리를 구현했으나, 한 프레임에 많은 이동이 일어나 분리/병합 과정에서 많은 연산이 들어가 동적 파티셔닝이 없는 구조로 완료함
      - 속도와 라이프타임 계산으로 충돌 연산 최적화: 플레이어와 적의 거리가 일정해, 플레이어와 적 탄환의 충돌 연산은 특정 시간에서만 검사하도록 함
    - 결과: 같은 테스트 기기에서 700개 수준에서 60프레임 유지 성공
